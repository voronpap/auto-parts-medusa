# Вимоги до магазину автозапчастин auto-parts.pp.ua

Документ поповнюється поступово: вимоги до етапу деталізуються перед початком
роботи над ним. Кожна вимога має ідентифікатор, на який можна посилатися в
комітах і обговореннях.

Стани вимог: `узгоджено` — погоджено власником; `чернетка` — запропоновано,
чекає на підтвердження; `зроблено` — реалізовано й розгорнуто.

## 1. Обсяг

### 1.1. Що входить

| Блок | Зміст | Етап |
|---|---|---|
| Каталог і номери | бренди, джерела, номери запчастин, нормалізація, пошук за номером | 1 |
| Кроси й докази | типізовані зв'язки між номерами, спостереження, статуси | 1 |
| Прайси й склад | імпорт CSV/XLSX постачальників, ціни, наявність, залишки | 2 |
| Вітрина й замовлення | storefront, кошик, оформлення, LiqPay, післяплата, Нова Пошта | 3 |
| Автомобілі й застосовність | довідник авто, VIN, підбір за авто, кваліфікатори | 4 |
| Зовнішні каталоги | TecDoc, EPC, каталоги виробників — за наявності ліцензій | 5 |
| Адмінка й правові вимоги | наскрізно, разом із кожним блоком | 1–5 |

### 1.2. Що не входить

| Що | Рішення |
|---|---|
| Електросхеми й діагностика | виключено власником 2026-10-12 |
| OCR і комп'ютерний зір, пошук за фото й етикеткою | виключено власником 2026-10-12 |
| AI для товарів і підбору | розробляється окремо (репозиторій `voronpap/codex-dev-hub`); у магазині лише точка підключення |

Пошук за EAN/GTIN як за звичайним номером лишається в обсязі: зображення для
нього не потрібні.

### 1.3. Джерела вимог

- Цільова специфікація власника з 15 розділів (2026-10-12).
- Архітектурні документи репозиторію `voronpap/automotive-parts-ai`:
  `docs/RELATIONS.md`, `docs/PRE_CODE_RESEARCH.md`, `docs/RIGHTS_DERIVATION.md`.

## 2. Наскрізні принципи

Ці правила діють для всіх етапів і закладаються в модель даних із першого дня.

| ID | Вимога | Стан |
|---|---|---|
| P-01 | AI не створює підтверджені OEM-кроси або застосовність. Дані від AI зберігаються лише як кандидати. | узгоджено |
| P-02 | «Фізично схоже» і «підтверджено сумісне» — різні твердження з різними типами зв'язку. | узгоджено |
| P-03 | Спільна застосовність двох деталей сама по собі не робить їх взаємозамінними. | узгоджено |
| P-04 | Кожен факт має походження: джерело, запис або URL, версія каталогу, дата отримання, версія парсера. | узгоджено |
| P-05 | Джерела зі спільним першоджерелом рахуються як одна лінія доказів (два магазини на TecDoc — це одне підтвердження, а не два). | узгоджено |
| P-06 | Конфліктні джерела не перезаписують одне одного; конфлікт зберігається й показується. | узгоджено |
| P-07 | Дослівне формулювання джерела (reference, interchangeable, substitute, replaced by тощо) зберігається поруч із нормалізованим типом зв'язку. | узгоджено |
| P-08 | Історичні й замінені номери не видаляються і лишаються доступними в пошуку. | узгоджено |
| P-09 | Кожне джерело має ліцензійний клас; після завершення ліцензії похідні факти без інших підтверджень втрачають статус. | узгоджено |
| P-10 | Захищені каталоги не скрапляться й не зберігаються дампами. | узгоджено |

## 4. Етап 1. Каталог номерів і кроси

Стан етапу: `чернетка`, чекає на підтвердження власника.

Мета: мати в адмінці довідник брендів, номери запчастин із пошуком і таблицю
кросів із доказами. Наповнення на цьому етапі ручне; масовий імпорт — етап 2.

### 4.1. Бренди й джерела

| ID | Вимога |
|---|---|
| C-01 | Бренд має назву, тип (виробник авто, виробник запчастин, постачальник) і довільну кількість аліасів. |
| C-02 | Пошук бренду знаходить його за будь-яким аліасом без урахування регістру (VW і Volkswagen — один бренд). |
| C-03 | Реєстр джерел: назва, тип, ліцензійний клас (`OPEN`, `LICENSED`, `CACHE_LIMITED`, `REFERENCE_ONLY`, `USER_PROVIDED`, `WORKSHOP`), лінія походження, примітка про ліцензію. |

### 4.2. Номери запчастин

| ID | Вимога |
|---|---|
| N-01 | Номер зберігається у трьох поданнях: `source_number` (як у джерелі), `display_number` (для показу), ключі пошуку (нормалізовані). |
| N-02 | Тип номера: OEM, OES, aftermarket, supplier, trade, EAN/GTIN, competitor. |
| N-03 | Номер унікальний у просторі «бренд + тип + номер». Однаковий текст номера в різних брендів — різні записи. |
| N-04 | Нулі, префікси й суфікси не втрачаються в жодному поданні, крім ключів пошуку. |
| N-05 | Ключі пошуку будуються видаленням пробілів, дефісів, крапок і скісних рисок та зведенням до верхнього регістру. |
| N-06 | Номер можна прив'язати до варіанта товару магазину; номер без товару — припустимий стан. |

### 4.3. Пошук

| ID | Вимога |
|---|---|
| S-01 | Точний пошук за номером незалежно від пробілів, дефісів і регістру. |
| S-02 | Частковий пошук: за початком номера, від трьох символів. |
| S-03 | Пошук за старим номером повертає його разом із ланцюжком замін до актуального. |
| S-04 | Результат показує бренд, тип номера, прив'язаний товар і кількість кросів. |

### 4.4. Кроси

| ID | Вимога |
|---|---|
| R-01 | Крос — спрямований зв'язок між двома номерами з типом, станом твердження, вердиктом застосовності, умовами та строком дії. |
| R-02 | Типи зв'язків відповідають словнику `RELATIONS.md`. Універсального типу «еквівалент» немає. |
| R-03 | Стан твердження: `ASSERTED`, `INFERRED_CANDIDATE`, `DISPUTED`, `RETRACTED`. |
| R-04 | Вердикт застосовності: `ACCEPTED`, `CONDITIONAL`, `CANDIDATE`, `REJECTED`, `UNRESOLVED`. Стан і вердикт незалежні. |
| R-05 | `SUPERSEDES` не зберігається: це зворотне подання `SUPERSEDED_BY`, що виводиться запитом. |
| R-06 | Підтримуються ланцюжки A → B → C, один-до-багатьох, багато-до-одного, заміна комплектом і зняття без заміни. |
| R-07 | Негативний крос (`NOT_APPLICABLE_TO`, вердикт `REJECTED`) зберігає причину, чому деталь не підходить. |
| R-08 | Умови зв'язку на цьому етапі зберігаються структурованим JSON; у таблиці кваліфікаторів виносяться на етапі 4. |

### 4.5. Докази

| ID | Вимога |
|---|---|
| E-01 | Спостереження зберігає джерело, ідентифікатор запису або URL, версію каталогу, дату отримання, версію парсера і стан (активне, застаріле, відкликане). |
| E-02 | Крос пов'язаний з одним або кількома спостереженнями; для кожного зберігається дослівний текст джерела. |
| E-03 | Вердикт `ACCEPTED` встановлюється лише через workflow і лише за наявності щонайменше одного активного спостереження з джерела, що не є кандидатним. |
| E-04 | Кількість незалежних підтверджень рахується за лініями походження джерел, а не за кількістю спостережень. |
| E-05 | Якщо в кросу не лишилось активних спостережень, його вердикт знижується до `UNRESOLVED`. |

### 4.6. Адмінка

| ID | Вимога |
|---|---|
| U-01 | Сторінка пошуку за номером із переглядом кросів і їхніх доказів. |
| U-02 | Створення й редагування брендів, аліасів, джерел, номерів і кросів. |
| U-03 | Для кожного кросу видно тип, стан, вердикт, умови та список доказів із джерелами. |
| U-04 | Інтерфейс українською. |

### 4.7. Приймання етапу

- Unit-тести на нормалізацію номерів, включно з нулями, суфіксами й змішаним регістром.
- Перевірка на живих даних: ланцюжок заміни з трьох номерів і крос із двома доказами з однієї лінії походження рахується як одне підтвердження.
- Тести, lint і build проходять; міграція застосована після резервної копії.

## 5. Наступні етапи

Вимоги деталізуються перед початком кожного етапу.

- **Етап 2. Прайси й склад.** Формат приймання — поля з VDB-14: `oem_numbers`,
  `replacement_numbers`, `supplier_article`, авто, двигун, роки, ринок,
  `source_name`, `source_url`, `license_note`; dry-run, журнал імпорту,
  дедуплікація.
- **Етап 3. Вітрина й замовлення.** Основа вже є: storefront на Next.js
  (`apps/storefront`, з `medusajs/dtc-starter`). Лишається адаптація під
  запчастини, оплата й доставка.
- **Етап 4. Автомобілі й застосовність.**
- **Етап 5. Зовнішні каталоги.**
